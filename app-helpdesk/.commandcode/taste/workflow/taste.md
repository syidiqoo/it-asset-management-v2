# Workflow

- Prefers incremental, staged delivery: asks to build the UI layer first (with mock data) before wiring up backend/database work. Confidence: 0.5
- Wants changes verified "live": asks for the app to be started on a dev server (e.g., localhost:3000) and left running so they can click through and test in the browser, not just via automated checks — directly instructs the agent to launch it ("coba run dev", again "test run dev"). Confidence: 0.65
- Established "test run" verification routine (framed by the agent as "kebiasaan kita" — our usual habit): keep the pre-run check quick and targeted (package.json, middleware, .env, prisma schema), launch the dev server in the background, smoke-test with an HTTP request (PowerShell Invoke-WebRequest to localhost:3000), then visually verify in a real browser via agent-browser (open → snapshot → screenshot), review the screenshot for rendering errors, and close the browser session — leave the dev server running afterwards and offer to stop it later rather than killing it. When a change affects generated output (e.g. CSV/PDF export), verify end-to-end the same way: exercise the real flow in the browser (logging in with the seeded credentials when needed), locate the downloaded file (check agent-browser's tmp dir, then the Downloads folder), and read its contents to confirm the fix instead of trusting the code change. For plain UI/code edits, before opening the browser run a targeted typecheck (`npx tsc --noEmit`) plus ESLint scoped to only the changed files (`npx eslint components/login-form.tsx components/sidebar.tsx`) rather than a full-project lint. Confidence: 0.6
- Runs commands in Windows PowerShell as the default terminal and expects commands typed in their natural form to work there (`npm run dev`, not `npm.cmd run dev` or switching to another shell). Confidence: 0.6
- Prefers the least invasive, reversible fix for environment/system problems: chose `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` (no admin, LocalMachine untouched, reversible to Undefined) over changes that require elevated/system-wide scope. Confidence: 0.5
- When they reject a result ("hapus saja") or ask for an asset to be removed, expects a complete removal, not a disable-and-leave-it: the artifact/files are deleted and every reference (imports, CSS variables, keyframes, call sites) is stripped so the tree returns to its exact pre-change state — verified as identical to the last commit rather than merely "close", and re-checked with grep + typecheck + lint. Before deleting an asset file, grep the codebase first to confirm it isn't referenced anywhere else (e.g. confirmed "cocpit" was only used by login-form before removing the image). Confidence: 0.6
- Prefers delegating git operations to the agent — asks it to perform the actual `git commit` and `git push` rather than running the commands themselves. Responds "lanjutkan"/"continue" to authorize the agent to carry the commit+push through to completion. Confidence: 0.65
- Ships each piece of feature work on its own new feature branch (e.g. `feat/wiki-dokumentasi`) pushed to origin with `-u`, rather than committing to/master staying on the main branch — asks the agent to "push ke branch baru" and doesn't want the work merged into master behind their back. Confidence: 0.55
- Expects a commit/PR to contain only the requested feature: unrelated generated tooling files (e.g. `.commandcode/taste/*`) and pre-existing untracked assets are left in the working tree and called out, rather than swept in with `git add -A`. Confidence: 0.45
- Expects npm scripts (esp. `npm run dev`) to work directly from the repository root, without having to `cd` into a nested project subfolder — wants a permanent fix (e.g. a thin root `package.json` that delegates to the subproject) rather than a one-off workaround. Treats this as a durable constraint: the root `package.json` must be kept in place, with `dev`/`build`/`start`/`lint` continuing to delegate via `npm --prefix <subfolder> run <script>`. Confidence: 0.85
- Comfortable with the agent seeding demo/sample data into the dev database (via a re-runnable add/`--remove` script) so a new feature is immediately visible for click-through testing, rather than only being described. Confidence: 0.35
- Prefers delegating production deployment/migration execution to the agent via SSH remote access — offers to prepare SSH to the server so the agent runs the deploy steps directly, rather than just receiving a written guide to follow themselves. Confidence: 0.6
- When the user supplies a reference website URL as the benchmark for a UI change, treat it as a visual spec: web_fetch can't render JS-built pages, so inspect it live instead (agent-browser open → screenshot → scroll to capture the full layout), extract concrete proportions from it (card width, inner padding, centered title, footer strip), mirror them in the implementation, then screenshot-compare the result against the reference before calling it done. Confidence: 0.7
- Maintains a detailed deployment runbook (`DEPLOY-UBUNTU.md`) for the production Ubuntu server and treats it as a living document that must stay in sync with the code: after feature work they proactively ask whether the docs are "masih sama atau ada perubahan". Verify doc accuracy by diffing the actual repo state (git status/diff/log) against each docs section (system deps/package.json, Prisma migrations, .env variables, auth/upload behavior, nginx/pm2 config) — update docs only when deploy-relevant areas changed; purely client-side UI changes leave the runbook valid as-is. Confidence: 0.5
- App-helpdesk dev login used for authenticated browser verification: username `admin` / password `admin123` (seeded dev credentials) — fill the username and password refs, click login, then navigate; needed whenever pages must be tested as admin. Confidence: 0.8
- For reported UI bugs ("control doesn't work"): reproduce the exact interaction in a fresh browser session and read the browser console before changing any code — if it works fresh, suspect the user's stale hot-reload bundle (successive hot reloads leaving an old/new handler mix in their open tab) and advise a hard refresh (Ctrl+Shift+R or reopening the tab) instead of patching blindly. To debug keyboard-event delivery, register a capture-phase window keydown listener that stores `e.key` (e.g. `window.__lastKey`) and inspect it via agent-browser `eval`; drive real keyboard input with agent-browser `press` (run `press --help` first when unsure of syntax), and reload the page before concluding `press` is broken — it worked once the page was freshly loaded. Confidence: 0.6
- For destructive local-database operations (e.g. wiping all seeded data), follows a careful, verifiable routine rather than a blind truncate: inspect the Prisma schema first to map FK relations, count rows per table before deleting, delete child tables before parents (FK-safe order), reset id sequences afterward (`SELECT setval(pg_get_serial_sequence('<Table>', 'id'), 1, false)`), re-count to confirm 0, and delete the temporary script used so no leftovers remain. When `psql` isn't installed, uses the project's existing tooling (a throwaway Node script with Prisma Client) instead of installing new tools. Reports exactly what was deleted (with per-table counts) plus side effects the user must know (e.g. admin user removed → login unavailable until re-seeded). Confidence: 0.5
- Masks credentials when inspecting files that contain secrets: reads `.env` through a filter (`cat .env | sed 's/PASSWORD=.*/PASSWORD=***/'`) so passwords never appear in terminal output. Confidence: 0.45
