# Taste
- Prefers communication in Bahasa Indonesia (Indonesian). Confidence: 0.9
- Prefers compact, space-saving display of hierarchical values (e.g. nested department paths) using only the leaf/last name, consistently across both table views and detail/preview dialogs, to avoid cluttered output. Confidence: 0.8
- Prefers numeric dd/mm/yyyy format for all displayed dates. Confidence: 0.9
- Prefers minimal, no-overengineering implementations — only necessary code so features run smoothly, avoids excessive/unneeded work. Confidence: 0.95
- Avoids Docker for local development, prefers lightweight native installs due to heaviness and storage cost. Confidence: 0.85
- Prefers storing uploaded files (images/documents) as binary rows in the local database rather than setting up filesystem or external object storage; prioritizes simplicity, portability, and automatic backup for small apps over storage-scale concerns. Confidence: 0.75
- Wants strict, explicit allowlists for accepted file types and low size limits (e.g. png/jpg/jpeg for images, pdf for documents, max 2 MB), defined in a single shared source used by both client and server so validation can never diverge. Confidence: 0.6
- Prefers preview/detail dialogs sized generously (wider dialog, larger image box, note/text areas, and labels) so information is easy to read, prioritizing legibility when inspecting a single item; treats a cramped note box as something to be enlarged rather than left small. Confidence: 0.65
- Prefers secondary/utility actions (e.g. a "view PDF" document button) placed in the dialog header instead of as a card/row inside a content column, so the action does not consume space in or disturb the balance of the main content. Confidence: 0.6
- Prefers images to fill their container edge-to-edge via `object-fit: cover` (full, cropped overflow) rather than leaving empty margins or stretching/distorting proportions. Confidence: 0.65
- Cares strongly about balanced whitespace: dislikes excessive/empty white space, wants the amount of visual content (image) and information detail balanced against each other, and in two-column layouts expects columns of equal height aligned at the same top/bottom with no leftover gap under a shorter column; explicitly calls out pairs of side-by-side cards (e.g. the map card beside the Asset Condition donut card) to be locked to identical height. Confidence: 0.75
- Wants the primary chart/graphic (e.g. the donut) rendered noticeably large and prominent, with its supporting legend/detail kept to a minimum — prefers shrinking or dropping the per-item detail (e.g. removing percentages, collapsing a 4-row legend into a compact two-column list of color dot + name + count) so the freed space goes to the visualization rather than the text. Confidence: 0.6
- In preview/detail views, prefers the visual (image/photo) placed in the left column with the textual details grouped on the right, rather than putting the image on the right or embedded as a row inside the detail list. Confidence: 0.55
- Expects the agent to step back and judge a UI/layout as a whole (balancing imagery against information) before editing, rather than optimizing isolated elements. Confidence: 0.6
- Reviews visual/UI results in the running app and gives short, subjective feedback (e.g. "placement is very bad", "uncomfortable to look at"), expecting the agent to infer the problem and propose concrete layout alternatives to choose from. Confidence: 0.5
- Reports bugs/failures as terse, non-technical "fix X" requests with no reproduction detail and often no description of the symptom (e.g. "aku tidak bisa sign in, tidak ada respon" — no URL, no error text; "perbaiki menu location" without saying what is broken), and expects the agent to investigate on its own (check the server, exercise the feature in the running app, test candidate paths) and then state the exact root cause plus the correct URL/steps or what was changed, rather than being asked for more details first. Confidence: 0.6
- Supplies UI design mockups/screenshots (e.g. images saved in a project folder like `sample-import`) or links to public design references (e.g. a Dribbble shot URL) and expects the agent to study them and faithfully replicate the layout/structure in the implemented component, rather than improvising a design. Confidence: 0.8
- When replicating a reference that contains an asset not yet available (e.g. a hero/brand image), wants the exact placement reserved but left as an empty placeholder driven by a single easily-editable constant at the top of the file (e.g. `const loginImageUrl = ""`), so the user can drop in the real URL later without restructuring the layout; prefers this over inventing a substitute image. Confidence: 0.6
- Prefers UI work to follow a referenced design's structure faithfully while omitting example-only elements that have no backing feature in the app (e.g. skipped "Sign up with Google", "Remember me", extra links) rather than rendering dead controls, and expects to be told explicitly what was left out and why. Confidence: 0.55
- Insists on data completeness in UI: every piece of information must appear, and none may be shown twice (no missing/missed information and no duplicate information); each field/value should render exactly once. Confidence: 0.8
- Prefers values shown as labelled fields inside the detail/section card rather than as chips or badges in a dialog header, because header chips are harder to read; prioritizes field legibility over decorative/compact header presentation. Confidence: 0.6
- Dislikes redundant/duplicate controls in the UI: wants only one close affordance per dialog (e.g. removes the header X when a footer "Close" button already exists), and expects the freed space to be reclaimed so remaining elements sit precisely. Confidence: 0.55
- Prefers action buttons in a footer ordered by function with the neutral Close button last (e.g. Move → Edit → Delete → Close), rather than Close first. Confidence: 0.5
- Prefers dropping fields whose value is effectively constant/predictable and therefore uninformative (e.g. removing "Updated By" because it is always the admin), treating them as noise; when a field is removed, expects the remaining layout rebalanced (no empty grid cells) to compensate. States this emphatically and expects it honored without needing to ask twice. Confidence: 0.7
- When told to hide/remove/change a UI element, expects it applied everywhere that element appears (e.g. both the preview dialog and the edit form), not only on the surface currently under review; a single-surface fix is treated as an incomplete change and the instruction must not need repeating. Confidence: 0.75
- Targets Ubuntu Server 22.04 as the production/hosting environment and expects concrete native install steps (apt packages, Node.js via NodeSource, PostgreSQL, nginx, pm2/systemd) rather than containerized/Docker deployment. Confidence: 0.55
- Prefers guidance/documentation delivered as a written markdown file inside the project (e.g. `DEPLOY-UBUNTU.md`) rather than only as prose in the chat, so the content is persisted and reusable. Confidence: 0.6
- When following setup/deployment/ops instructions step by step, expects each command to state explicitly which environment/prompt it belongs to (e.g. Linux shell vs. inside `psql`), since ambiguity about where to run a command causes confusion and follow-up questions. Confidence: 0.55
- Asks clarifying questions about raw CLI/shell syntax (e.g. whether `$USER:$USER` should be typed literally or replaced with the actual username); prefers instructions that spell out literal values, or explicitly say what to substitute and that quote style matters. Confidence: 0.5
- Expects the agent to investigate autonomously rather than only hand back commands: when a step fails, prefers the agent to connect to the server via SSH itself and run diagnostics (check versions, reproduce the command, read the full error) instead of asking the user to paste output or run it manually. Readily hands over raw server credentials (`user@host` + password) when asked and expects the agent to then execute the deployment/diagnostic steps directly on that server end-to-end rather than continuing to relay instructions for the user to run. Confidence: 0.75
- Prefers compact form layouts that save vertical space: related fields (e.g. notes and file uploads) grouped into a single row/card with a side-by-side two-column grid rather than stacked as separate full-width sections, and expects the shorter field (e.g. a textarea) to stretch to match the taller column. Confidence: 0.65
- Prefers pm2 as the process manager for the deployed Node/Next.js app: global install, app bound to localhost, `pm2 save` plus `pm2 startup systemd` so it auto-restarts on crash and auto-starts after a reboot. Confidence: 0.6
- When a production behavior conflicts with local/LAN access (e.g. `Secure` session cookies over plain HTTP causing login loops), prefers solving it at the infrastructure layer with nginx as reverse proxy plus a self-signed TLS certificate and HTTP→HTTPS redirect, rather than modifying the application code or skipping the issue. Confidence: 0.55
- Once the missing input is provided (e.g. the admin password), expects the agent to write it straight into the server's `.env` and finish the remaining deployment steps end-to-end without pausing for further confirmation. Confidence: 0.5
- Prefers the production database to start clean: create only the admin user and skip dummy/sample seed data that would have to be deleted by hand afterward. Confidence: 0.5
- For map/geospatial features, prefers a real interactive map (Leaflet with OpenStreetMap online tiles — zoom/pan, clickable markers) over an offline static/vector (SVG) rendering, accepting the need for internet access to load the basemap. Confidence: 0.55
- Prefers the main dashboard to lead with a personalized greeting header naming the logged-in user (e.g. "Selamat datang, {nama}"), followed by the visual map, and only then the numeric summary cards — personalization and visual content rank above stat summaries in top-to-bottom ordering. Confidence: 0.5
- Expects new features to match the patterns already used elsewhere in the app ("seperti menu lainnya"): when asking to add a capability, wants it implemented with the same shared components and conventions as the existing menus (e.g. the shared FilterBar/StickyHeader layout, URL-query-based filtering via a common helper, consistent reset/empty-state behavior) rather than a bespoke one-off implementation, and wants the change rolled out consistently across all equivalent menus. Confidence: 0.6
- Prefers blocked/destructive actions to fail loudly instead of silently: when a delete is refused (e.g. the record is still referenced elsewhere), wants the control disabled with a visible reason/tooltip and any runtime failure surfaced as an explicit error inside the confirm dialog, and wants this handling applied consistently across all equivalent menus — rather than the dialog quietly doing nothing or silently cascading/detaching the references. Confidence: 0.6
- Wants the dashboard map locked to the relevant area (Indonesia): default view centered/fit to the country with panning and zoom-out clamped (maxBounds, minZoom, non-repeating tiles) so it cannot be dragged or zoomed out to the world map. Confidence: 0.5
- In hierarchical lists/trees, prefers depth conveyed purely by indentation and any explicit level/number badge (e.g. "Lv N") removed as redundant decoration. Confidence: 0.6
- Prefers tree/hierarchy nodes to expose an interactive expand/collapse control (a clickable chevron that toggles children) styled like the app's existing clickable icon buttons (e.g. the "+" add button), rather than a static or non-interactive hierarchy display. Confidence: 0.55
